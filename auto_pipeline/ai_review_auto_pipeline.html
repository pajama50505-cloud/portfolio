CI/CD 배포 자동화 파이프라인

TV/OTT 광고 캠페인 관리 플랫폼 (SMAP)

배경

3인 개발팀, 주 1~2회 배포. 기존 방식은 환경별 배포 스크립트를 머지 후 수동 실행했다. 문제는 스크립트 자체가 아니라 사람이 개입하는 구간에 있었다.

  • 환경 혼동 — 배포할 환경과 스크립트를 개발자가 직접 매칭. dev용 스크립트를 prod에 돌리거나 반대의 가능성이 항상 존재했다.
  • 배포 내역 미공유 — "지금 나간 게 뭐야?"를 팀이 공유하지 않으면 모름. 사고가 나도 원인 추적이 늦다.
  • 수동 롤백 — 잘못 나갔을 때 버전을 확인하고 스크립트를 다시 실행. 장애 상황에서 판단할 여력을 낭비했다.

주 1~2회지만 광고 송출에 직접 영향을 미치는 시스템이라 배포 자체에 불필요한 긴장이 있었다.

목표

  • 환경 혼동 제거 — dev/prod 배포가 구조적으로 분리되어야 한다
  • 팀 전체가 배포 시점과 내용을 자동으로 공유받아야 한다
  • 롤백을 버튼 하나로 — 장애 상황에서 판단할 여력만 남기기
  • 추가 인프라 없이 — 주 1~2회 배포에 상시 서버를 두는 건 낭비

설계 결정

이메일 버튼 승인 방식

자동 배포(push → 즉시 배포)가 아닌 이메일 승인을 선택한 이유: 팀이 작을수록 "지금 배포하면 되나?"의 판단이 중요하다. 광고 송출 시스템은 캠페인 일정에 따라 배포 타이밍을 고려해야 하는 경우가 있다. 자동화하되 최종 트리거는 사람이 누르는 구조를 유지했다.

Lambda로 트리거 서버를 대체

주 1~2회 트리거를 위해 상시 서버를 운영하는 건 낭비다. Lambda Function URL은 별도 서버 없이 HTTP 엔드포인트를 제공하고 실행 시간만 과금된다. 배포 빈도가 낮은 프로젝트에서 운영 부담 없이 신뢰성 있는 트리거를 만들 수 있다.

Docker 태그에 빌드 번호 + 타임스탬프

롤백 시 어떤 이미지가 어느 시점 것인지 식별할 수 있어야 한다. {env}-{N}-{YYYYMMDDHH} 형식은 순서(N)와 시각 둘 다 담는다. 별도 배포 이력 DB 없이 이미지 태그만으로 롤백 대상을 특정할 수 있다.

HMAC 서명 URL

이메일 버튼에 단순 토큰을 쓰면 링크 재사용이 가능하다. HMAC-SHA256 서명 + 2시간 만료로 위변조와 재사용을 차단했다. Lambda에서 서명 검증만 하면 되어 DB 없이 stateless하게 구현할 수 있다.

LLM 코드리뷰 자동화

코드리뷰는 CI/CD의 첫 번째 관문이다. 기존에는 팀원 리뷰에만 의존했는데, 3인 팀에서 모든 PR을 꼼꼼하게 보는 건 현실적으로 어렵다. PR 등록 시 Claude CLI가 diff를 분석해 1차 리뷰 결과를 이메일로 발송하고, 팀원은 LLM 의견을 참고해 최종 판단한다.

Anthropic API를 별도 계약하지 않고 기존 구독(Claude Team Plan)의 CLI를 활용해 추가 비용 없이 운영한다. Claude CLI는 OAuth 인증 방식으로 Lambda 실행 불가 — Bitbucket Webhook 수신 겸 전용 서버를 별도 운영한다. diff 규모에 따라 전체 or 파일별 분할 처리로 컨텍스트 한계를 우회한다.
